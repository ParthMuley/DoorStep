# Doorstep decisions (owned by Developer B)

Synthetic-data simulation only. These decisions cover the domain engine, backend, and simulator.

| # | Decision | Why |
|---|---|---|
| B-01 | New cases start `resident_status=UNKNOWN`, not `NEEDS_ASSISTANCE`. | Silence is not evidence. `NEEDS_ASSISTANCE` only after an explicit request. |
| B-02 | `Assignment.status` uses the **service** vocabulary (`AWAITING_PROVIDER`, `ACCEPTED`, `COMPLETED`, ...). Resident vocabulary (`PROVIDER_ACCEPTED`, ...) lives only on the case. | Keeps the three state dimensions separate. The master spec's sample JSON shows `status: PROVIDER_ACCEPTED` on an assignment; we read that as illustrative. |
| B-03 | `zone_3` is the simulated warning area. Residents live in its sectors: `zone_3_sector_b` (Maria, outside) and `zone_3_sector_a` (David, active simulated order). Case `zone_id` is `zone_3`; `sector_id` drives the zone rule and routing. An unknown location is `UNVERIFIED` and blocks assignment. | Matches contract v1.0 Section 5. One warning starts both scenarios. |
| B-04 | Edge `zone_3_sector_b`–`zone_4` is closed. The planner avoids closed edges and every active-order zone, and labels routes "illustrative only". | Shows the blocked-road rule without claiming any route is safe. |
| B-05 | Pickup = provider **and** resident/caregiver confirmed. Arrival = `DESTINATION_CHECKIN` by the accepted destination provider, **or** resident/caregiver plus transport provider, and always an accepted destination. Optional identified `confirmations` are checked against the real participants. | Contract v1.0 evidence format, plus identity checks proposed for v1.1. |
| B-06 | Free-text parsing is deterministic keyword matching (EN/ES). It produces candidate needs only; nothing is used until the resident replies YES/SÍ . | No LLM needed for P0. An LLM extractor can be added later under the same confirm-first contract. |
| B-07 | No eligible transport (including an empty offer list) means the request becomes `UNRESOLVED` and the case becomes `REQUIRES_COORDINATOR` automatically, with an explicit next step. Escalation is a separate, explicit call. | Every unfulfilled request stays visible; escalation leaves a record. |
| B-08 | Escalation acknowledgment is `ACKNOWLEDGED_REQUEST_ONLY` with `assistance_confirmed=false`, always. The no-acknowledgment branch is switched on with `POST /sim/escalation-ack`. | Spec rule 9. |
| B-09 | The simulator never makes up delivery receipts. Outbound messages stay `SENT` until a receipt is injected (`POST /sim/delivery`). | Spec Section 4: don't make up receipts. |
| B-10 | IDs (`assign_001`, `evt_001`, `resp_001`...) come from DB counters, so a reset followed by the same calls gives identical IDs. Case IDs are fixed per resident (`case_maria_001`, `case_david_002`). | `reset_demo.sh` must reproduce identical state. |
| B-11 | Write endpoints require `Authorization: Bearer $DEMO_AUTH_TOKEN`; reads are open. Provider writes also check `provider_id` against the assignment and the registry. | Contract v1.0 Section 3. Demo gating, not production auth. |
| B-12 | One active accepted assignment per (case, service type) is enforced by a MongoDB partial unique index on `_accepted_slot` (set only while ACCEPTED/COMPLETED). | Atomic acceptance; duplicate or delayed replies cannot create a second assignment. |
| B-13 | `request_recovery_handoff` requires `granted_by` (`RESIDENT`/`CAREGIVER`, mapped to the party ID). No consent means 409 `CONSENT_MISSING`, with the decline still recorded. Confirmed arrival is not required. | Consent must be attributable. Contract v1.0 3.10. |
| B-14 | The Spanish templates in `services/templates.py` are **not yet reviewed** by a fluent speaker. They must be reviewed before the demo. | Spec Section 8: use a reviewed translation. |
| B-15 | The backend refuses to start unless `SIMULATION_MODE=true`. | Spec safety boundary. |
| B-16 | B no longer owns provider inventories. A's provider agents send raw offers; B evaluates them against a **partner approval registry** (approval + base zone). Approval is never taken from the offer. | Contract v1.0 design note: providers never read B's database. |
| B-17 | A proposal pairing transport and destination is stored as two linked assignment rows under one public `assignment_id`. Each provider accepts on that id with its own `provider_id`. | Keeps the one-accepted-per-service unique index, and destination acceptance stays explicit. |
| B-18 | Offers are re-evaluated at proposal time (expiry, approval, zone, consent). Expired or unparseable `valid_until` means rejected. | Stale availability must not slip through. |
| B-19 | Safety and business-rule refusals are HTTP 409 with contract codes; request validation is 422. | Contract v1.0 Section 3. |
| B-20 | Storage moved from SQLite to **MongoDB** (`doorstep_users` + `doorstep_orgs`; mongomock offline). There are no multi-collection transactions, so every operation checks all of its guards **before** its first write; contention is handled by single-document atomics (unique indexes, conditional updates, `$inc` counters). `db.tx()` only serializes writes within the process. | Team decision for a NoSQL store; mongomock can't do transactions, and validate-first keeps failures write-free. |
| B-21 | Without `MONGODB_URI`, the backend runs on in-memory mongomock; `scripts/start_mongo.sh` gives a persistent local MongoDB. Index creation skips indexes that already exist (restart-safe). | Works offline with zero setup, and persists when a server is available. |
| B-22 | Residents are stored in the v2 shape (needs codes, emergency contacts, purpose consents). Until the v2 switch-over, the v1 engine reads them through `services/legacy.py`; seeded residents carry an internal `_legacy_sector` for the v1 zone rule, and API-registered residents fail closed (UNVERIFIED). | Lets B2 land without breaking the working v1 flow A uses today. |
| B-23 | A volunteer's availability is tied to one alert: the alert outreach last asked about (or the first answer). Answers for any other alert → 409 `STALE_AVAILABILITY`; unapproved volunteers can't answer; repeated answers are idempotent via `provider_events`. `recovery_services` uses help types (`TEMPORARY_HOUSING`…), not service names. | Old answers must never make a volunteer look available for a new calamity. |
| B-24 | No feed data (nothing ingested yet) → every resident is `UNKNOWN`, including at registration. A stale simulated feed → every resident is `STALE`, and no check-ins or outreach are triggered from stale data. | V2 rule: missing or stale data never means safe. |
| B-25 | Synthetic `CANCEL` sets `STATUS "Normal"` (explicit lift, immediate). `EXPIRE` removes the record (2-miss rule). A failed fetch never cancels anything. Live `REAL_WORLD` alerts are stored for display only and never affect residents, check-ins or outreach. | Mirrors Cal OES behaviour, including its rebuild gap. |
| B-26 | Volunteer outreach is per alert: it sets approved volunteers to `ASKED` for that alert (which replaces earlier answers). SMS replies from a volunteer's phone are routed by `/sim/inbound`. The stale-alert check runs before idempotency, so a replayed old answer is refused rather than echoed. The message rate limit is per recipient. | Old availability must never count for a new calamity. |
| B-27 | A volunteer's YES counts for any currently active simulated alert of the same calamity type (one wildfire can have several zone records, e.g. a WARNING and an ORDER). Answers tied to a canceled alert don't count. Reservation uses the same set. | Outreach is per event; otherwise a volunteer asked about one zone would look unasked for the neighboring zone. |
| B-28 | Every fresh ingest offers check-ins to residents inside any active simulated WARNING/ORDER zone, deduped by (alert, status, resident). | People who register after an alert is issued must still be asked. |
| B-29 | Volunteer acceptance re-checks the resident's zone and the reservation. Declines release the reservation, cancel an unaccepted linked shelter row, and name the next eligible volunteer. A shelter bed is taken atomically on shelter acceptance; the volunteer is released at arrival. When the resident's own zone blocks matching, that zone code leads every volunteer's reasons. | Zones change between proposal and acceptance; cards must show the real reason. |
| B-30 | Plan rev 3 adopted: partners are location-first in `doorstep_partners.regions` (area → orgs → local volunteers/sites) with a canonical `organizations` collection. Each volunteer belongs to one org and one region. Org fact updates are copied into every region in the same request. | Team decision: we only ever want the nearest available helpers (an LA fire never contacts SF volunteers), and location is the query key. |
| B-31 | Nested region edits use optimistic compare-and-swap on a `_rev` field (read, change, write only if unchanged, retry). Reservations, availability and beds stay atomic on mongomock and real MongoDB. Geo: real MongoDB pre-filters with `2dsphere` `$geoIntersects`; mongomock (no geo operators) scans; both finish with the same Shapely distance, so results are identical. | Works in tests and in the live demo without two code paths for the rules. |
| B-32 | One Volunteer Network agent replaces per-org agents. Its routes need `X-Agent-Token`, and B checks `org_id` membership on every network write. Outreach selects orgs by region distance within each org's own radius (only regions with volunteers). Agent addresses come from `PUT /agents/{role}`. A resident `PICKED UP`/`RECOGIDO` SMS records the resident side of pickup. | Answers A's review items 1–5; fits the 8-agent Agentverse cap. |
